=== Punto de entrada de la aplicación

`app/layout.tsx` es el layout raíz de Next.js App Router: define metadata SEO/OpenGraph/Twitter (líneas 6-48), registra la fuente `GeistSans` vía `geist/font/sans` (línea 2), fija `<html lang="es">` de forma estática (línea 56) y monta el componente cliente `HtmlLangSync` antes de renderizar `children` (línea 62).

`next.config.ts` configura el modo de export estático:

[source,typescript]
----
const nextConfig: NextConfig = {
  output: "export",
  images: { unoptimized: true },
  eslint: { ignoreDuringBuilds: true },
};
----
(`next.config.ts:3-10`). `output: "export"` implica que no hay servidor Next.js en producción — el resultado de `next build` es HTML/CSS/JS estático en `out/`, servido íntegramente por CloudFront/S3. `images.unoptimized: true` es consistente con esa restricción (el optimizador de imágenes de Next.js requiere un servidor). `eslint.ignoreDuringBuilds: true` desacopla el lint del build de Next.js; el pipeline de CI ejecuta `npm run lint` como paso separado y previo al build (`.github/workflows/pipeline.yml:200-204`), por lo que el lint sigue siendo un gate real, solo que no bloquea `next build` en ejecuciones locales.

=== Internacionalización propia (sin librería de terceros)

`app/i18n/locale.ts` define el tipo `Locale = "es" | "en"` y el locale por defecto `"es"` (líneas 1-5). `app/i18n/paths.ts` mapea explícitamente cada ruta española a su equivalente en inglés en un arreglo `pathPairs` (líneas 3-9) y expone dos funciones puras:

* `localeFromPathname(pathname)`: determina el locale por prefijo `/en` (líneas 11-12).
* `getAlternatePath(pathname, target)`: resuelve la ruta equivalente en el locale destino para el selector de idioma (líneas 15-19), usada por `navbar.tsx` para el switch de idioma y por `HtmlLangSync`.

`app/i18n/dictionary.ts` (580 líneas) exporta un tipo `Dictionary` con secciones por área de UI (`nav`, `footer`, `hero`, `trustBar`, `valueProp`, `contact`, `whatsapp`, etc.) y una función `getDictionary(locale)` que devuelve el diccionario completo para ese locale. Los componentes cliente (p. ej. `contact.tsx`, `whatsapp-button.tsx`) llaman `getDictionary(locale)` para obtener sus textos.

=== Infraestructura AWS CDK (`infra/`)

Entry point (`infra/bin/codelabs-web.ts:1-13`): crea la `cdk.App`, lee el contexto `stage` (por defecto `"prod"`) e instancia `StaticSiteStack` con la configuración resuelta por `getEnvironmentConfig(stage)`.

`infra/lib/config.ts` define `StaticSiteConfig` y una única configuración real, `prodConfig` (líneas 16-34): `stackName: "CodelabsWebProdStack"`, región `us-east-1`, dominio `codelabsecuador.com` + alterno `www.codelabsecuador.com`, y los datos del repositorio de GitHub (`githubOwner: "FrancisU20"`, `githubRepository: "CodelabsWeb"`, `githubBranch: "master"`) usados para restringir el rol OIDC. `getEnvironmentConfig` lanza `Error` para cualquier `stage` distinto de `"prod"` (líneas 36-42): no hay ambiente de staging modelado en código.

`infra/lib/static-site-stack.ts` (`StaticSiteStack`, líneas 56-241) compone, en este orden:

. `HostedZone.fromLookup` sobre `hostedZoneDomainName` (línea 62).
. `Certificate` ACM con validación DNS sobre esa zona, incluyendo el dominio alterno (líneas 66-70).
. `Bucket` S3 privado: `BLOCK_ALL`, cifrado gestionado por S3, SSL forzado, `BUCKET_OWNER_ENFORCED`, versionado, `RemovalPolicy.RETAIN` (líneas 72-79).
. `Function` de CloudFront (CloudFront Functions, no Lambda@Edge) que reescribe URLs limpias a `.html` o `index.html` para soportar el export estático de Next.js (líneas 81-99).
. `Distribution` con esa función asociada al evento `VIEWER_REQUEST`, origen S3 vía Origin Access Control, `ResponseHeadersPolicy.SECURITY_HEADERS`, `CachePolicy.CACHING_OPTIMIZED`, redirección forzada a HTTPS, TLS mínimo 1.2 (2021), HTTP/2 y HTTP/3, páginas de error 403/404 mapeadas a `/404.html` (líneas 101-136).
. Registros `ARecord`/`AaaaRecord` alias hacia la distribución para cada dominio configurado (líneas 138-153).
. Rol IAM `GitHubActionsDeployRole` asumible vía OIDC de GitHub Actions, con permisos acotados a subir/borrar objetos en el bucket del sitio e invalidar la distribución CloudFront concreta (método `createGitHubDeployRole`, líneas 174-231).

Salidas (`CfnOutput`, líneas 157-171): URL del sitio, nombre del bucket, ID y dominio de la distribución CloudFront, y ARN del rol de despliegue — estos valores son los que se cargan manualmente como variables de repositorio de GitHub según `infra/README.md`.

=== Patrones notables

* Separación estricta build-time/deploy-time: el export estático (`out/`) se construye una sola vez en el job `web-quality` y se reutiliza como artefacto (`actions/upload-artifact` / `download-artifact`) en el job `deploy-web`, en lugar de reconstruirlo — evita divergencia entre lo validado y lo publicado (`.github/workflows/pipeline.yml:214-221` y `267-271`).
* Cache-Control diferenciado en el despliegue: los assets versionados de Next.js bajo `_next/static` se suben con `public,max-age=31536000,immutable`, mientras el resto del sitio usa `public,max-age=300,must-revalidate` (`.github/workflows/pipeline.yml:287-300`), coherente con el hashing de archivos que aplica `next build`.
* Sin llaves de acceso de AWS estáticas en ningún flujo: tanto el pipeline de GitHub Actions como la propia stack CDK están diseñados alrededor de un proveedor OIDC (`infra/lib/static-site-stack.ts:179-193`, `.github/workflows/pipeline.yml:280-285`).
