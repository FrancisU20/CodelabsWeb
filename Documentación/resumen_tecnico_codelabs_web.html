2. Propósito funcional

CodelabsWeb es el sitio corporativo estático de CodeLabs Ecuador (empresa de ingeniería de software), construido con Next.js App Router y exportado como HTML/CSS/JS estático (output: "export" en next.config.ts:4). No expone backend propio ni rutas de API: toda interacción de contacto delega en enlaces mailto: y wa.me (WhatsApp) resueltos en el cliente.

Rutas reales verificadas en app/ (ver matriz completa en matrices/interfaces.csv):

  • Sitio en español (grupo de rutas (site)): / (app/(site)/page.tsx), /servicios (app/(site)/servicios/page.tsx), /casos (app/(site)/casos/page.tsx), /nosotros (app/(site)/nosotros/page.tsx), /contacto (app/(site)/contacto/page.tsx).

  • Sitio en inglés, bajo el mismo grupo (site): /en (app/(site)/en/page.tsx), /en/services, /en/case-studies, /en/about, /en/contact.

  • Páginas legales (grupo de rutas (legal), en español únicamente): /privacidad, /tratamiento-datos, /terminos, /desuscripcion.

El mapeo español↔inglés de rutas equivalentes está codificado explícitamente en app/i18n/paths.ts:3-9 (pathPairs), no mediante enrutamiento de Next.js basado en segmentos [locale].

Alcance verificado: presentación institucional (propuesta de valor, capacidades, casos de éxito, stack tecnológico, clientes), captación de contacto (formulario que abre WhatsApp), y contenido legal (privacidad, tratamiento de datos, términos, desuscripción) conforme a LOPDP (Ecuador). No hay autenticación, panel de administración, ni persistencia de datos de negocio.

3. Arquitectura

Next.js App Router con dos grupos de rutas paralelos que comparten el layout raíz:

  • app/layout.tsx (raíz): define metadata global (título, OpenGraph, Twitter card, íconos, manifest — líneas 6-48), fuente GeistSans, monta <html lang="es"> fijo y el componente cliente HtmlLangSync (app/ui/html-lang-sync.tsx) que sincroniza document.documentElement.lang en cada navegación según la ruta (app/ui/html-lang-sync.tsx:7-15).

  • app/(site)/layout.tsx: layout del sitio público — envuelve el contenido con Navbar, Footer y el botón flotante WhatsAppButton (líneas 1-18).

  • app/(legal)/*: páginas legales autocontenidas, sin layout adicional propio (usan <main> directamente, p. ej. app/(legal)/privacidad/page.tsx).

Composición por secciones: cada página compone componentes de presentación reutilizables desde app/(site)/sections/ (17 archivos: hero, trust-bar, value-prop, clients, capabilities/-teaser, case-studies/-teaser, cta-banner, contact/-info, navbar, footer, about, aws-showcase, how-we-work, tech-stack). Los datos de contenido (clientes, capacidades, casos, stack) están en módulos TypeScript planos bajo app/data/, no en un CMS ni API externa.

Internacionalización: implementación propia por diccionario (app/i18n/dictionary.ts, 580 líneas) indexado por Locale ("es" | "en", app/i18n/locale.ts), sin librería de i18n de terceros (no usa next-intl ni next-i18next). Cada componente cliente que necesita texto localizado recibe la prop locale y llama getDictionary(locale).

Estilos: Tailwind CSS 4 vía @import "tailwindcss" en app/globals.css:1 y el plugin @tailwindcss/postcss (postcss.config.mjs); variables de marca (--primary, --surface, etc.) definidas en :root (app/globals.css:3-11).

Infraestructura (infra/, paquete AWS CDK v2 independiente del build de Next.js): infra/bin/codelabs-web.ts instancia una única stack StaticSiteStack (infra/lib/static-site-stack.ts) usando configuración de infra/lib/config.ts, que solo admite el stage "prod" (lanza excepción para cualquier otro valor — infra/lib/config.ts:36-42). La stack compone: bucket S3 privado, distribución CloudFront con Origin Access Control, certificado ACM en us-east-1, registros alias Route 53, una CloudFront Function de reescritura de URLs limpias, y un rol IAM asumible vía OIDC de GitHub Actions. Detalle completo en modules/evidencia.adoc.

Publicación: pipeline único en .github/workflows/pipeline.yml que construye el export estático (npm run build → out/) y lo sincroniza a S3 + invalidación de CloudFront cuando corresponde. Flujo completo en modules/arquitectura_y_flujos.adoc.

6. Seguridad y contexto de ejecución

No hay autenticación ni autorización en la aplicación: es un sitio público sin sesiones, roles ni datos protegidos.

CloudFront (infra/lib/static-site-stack.ts): TLS mínimo SecurityPolicyProtocol.TLS_V1_2_2021 (línea 134), ViewerProtocolPolicy.REDIRECT_TO_HTTPS (línea 115), origen S3 servido únicamente vía Origin Access Control (S3BucketOrigin.withOriginAccessControl, línea 113 — el bucket no es accesible públicamente), y ResponseHeadersPolicy.SECURITY_HEADERS (línea 114), la política administrada de AWS para cabeceras de seguridad estándar. El código de este repositorio no define una política de cabeceras personalizada ni una Content-Security-Policy explícita; solo referencia la política administrada por nombre.

S3 (infra/lib/static-site-stack.ts:72-79): BlockPublicAccess.BLOCK_ALL, BucketEncryption.S3_MANAGED, enforceSSL: true, ObjectOwnership.BUCKET_OWNER_ENFORCED, versioned: true, RemovalPolicy.RETAIN (el bucket no se destruye si se elimina la stack).

Despliegue desde GitHub Actions: sin credenciales estáticas. El rol GitHubActionsDeployRole (infra/lib/static-site-stack.ts:174-231) se asume vía OIDC (token.actions.githubusercontent.com) con condición StringEquals que restringe el sub a repo:FrancisU20/CodelabsWeb:ref:refs/heads/master y repo:FrancisU20/CodelabsWeb:environment:production (líneas 190-193), con permisos IAM acotados a s3:PutObject/DeleteObject/GetBucketLocation/ListBucket/PutObjectTagging sobre el bucket del sitio y cloudfront:CreateInvalidation sobre la distribución concreta (líneas 210-226). El job deploy-web del pipeline usa el environment: production de GitHub (línea 262) y permisos mínimos id-token: write (línea 265).

No se detectaron secretos, claves ni credenciales en el código fuente del worktree. La configuración sensible de despliegue (rol a asumir, nombre del bucket, ID de distribución) se referencia por nombre de variable de repositorio de GitHub (AWS_ROLE_TO_ASSUME, SITE_BUCKET_NAME, CLOUDFRONT_DISTRIBUTION_ID, AWS_REGION), nunca por valor, tal como documenta infra/README.md.

No aplica: sitio estático sin persistencia propia. El bucket S3 de infra/ almacena únicamente los artefactos estáticos del export (out/) como hosting, no datos de negocio ni estado de aplicación. 9. Operación y configuración

Comandos declarados en package.json (raíz, app web): npm ci (setup), npm run dev (next dev), npm run build (next build, genera export estático en out/ por output: "export"), npm run start (serve out), npm run lint (eslint).

Comandos declarados en infra/package.json: npm run build (tsc --noEmit), npm run synth (cdk synth), npm run diff (cdk diff), y npm run cdk como passthrough a la CLI de CDK. infra/cdk.json fija el entry point (npx ts-node --prefer-ts-exts bin/codelabs-web.ts) y activa el contexto @aws-cdk/aws-cloudfront:defaultSecurityPolicyTLSv1.2_2021.

Pipeline real de publicación (.github/workflows/pipeline.yml, con las acciones compuestas .github/actions/setup-web/action.yml y .github/actions/setup-infra/action.yml): se dispara en pull request contra master, en push a master y por workflow_dispatch manual. Detecta cambios por ruta para decidir si valida web, valida infra, o despliega; el despliegue real a S3/CloudFront solo ocurre en push a master o dispatch manual con deploy_web=true, y requiere el environment: production de GitHub configurado con las variables de repositorio AWS_ROLE_TO_ASSUME, AWS_REGION, SITE_BUCKET_NAME, CLOUDFRONT_DISTRIBUTION_ID (usadas en pipeline.yml:57-61 y validadas explícitamente antes de desplegar en la línea 273-278).

Variables de entorno/configuración leídas por el código (solo nombres, sin valores): CDK_DEFAULT_ACCOUNT, CDK_DEFAULT_REGION/región fija us-east-1 (infra/lib/config.ts:20-21), GITHUB_OIDC_PROVIDER_ARN (override opcional, infra/lib/config.ts:29-33). El perfil de AWS local esperado para operaciones manuales de CDK es codelabs (documentado en README.md e infra/README.md, no forzado por código).

Esta tarea fue exclusivamente de documentación: no se ejecutó npm install/build/test, no se modificó ningún pipeline, secreto, variable de repositorio ni aplicación desplegada, y no se realizaron cambios de código en ningún checkout del repositorio.

  7. Rol IAM GitHubActionsDeployRole asumible vía OIDC de GitHub Actions, con permisos acotados a subir/borrar objetos en el bucket del sitio e invalidar la distribución CloudFront concreta (método createGitHubDeployRole, líneas 174-231).

Salidas (CfnOutput, líneas 157-171): URL del sitio, nombre del bucket, ID y dominio de la distribución CloudFront, y ARN del rol de despliegue — estos valores son los que se cargan manualmente como variables de repositorio de GitHub según infra/README.md.

Patrones notables

  • Separación estricta build-time/deploy-time: el export estático (out/) se construye una sola vez en el job web-quality y se reutiliza como artefacto (actions/upload-artifact / download-artifact) en el job deploy-web, en lugar de reconstruirlo — evita divergencia entre lo validado y lo publicado (.github/workflows/pipeline.yml:214-221 y 267-271).

  • Cache-Control diferenciado en el despliegue: los assets versionados de Next.js bajo _next/static se suben con public,max-age=31536000,immutable, mientras el resto del sitio usa public,max-age=300,must-revalidate (.github/workflows/pipeline.yml:287-300), coherente con el hashing de archivos que aplica next build.

  • Sin llaves de acceso de AWS estáticas en ningún flujo: tanto el pipeline de GitHub Actions como la propia stack CDK están diseñados alrededor de un proveedor OIDC (infra/lib/static-site-stack.ts:179-193, .github/workflows/pipeline.yml:280-285).

Anexo — Arquitectura y flujos técnicos

Flujo 1: resolución de locale y navegación bilingüe

El sitio no usa el mecanismo de rutas dinámicas [locale] de Next.js ni middleware de negociación de idioma; el bilingüismo es un mapeo manual entre dos árboles de páginas (español en la raíz de (site), inglés bajo (site)/en/).

  1. app/i18n/paths.ts:3-9 declara el mapa canónico de rutas equivalentes:

    const pathPairs: Array<[es: string, en: string]> = [
  ["/", "/en"],
  ["/servicios", "/en/services"],
  ["/casos", "/en/case-studies"],
  ["/nosotros", "/en/about"],
  ["/contacto", "/en/contact"],
];

  2. localeFromPathname(pathname) (app/i18n/paths.ts:11-12) clasifica cualquier ruta como "en" si es /en o empieza con /en/, y "es" en cualquier otro caso. Es la única fuente de verdad para "en qué idioma estoy" fuera de la página misma.

  3. Cada page.tsx invoca sus secciones pasando el locale correspondiente como literal (p. ej. app/(site)/page.tsx:19-25 pasa locale="es" a Hero, TrustBar, ValueProp, etc.; su contraparte app/(site)/en/page.tsx pasa locale="en"). El locale no se infiere en tiempo de ejecución dentro de la página: está fijado por en qué archivo vive.

  4. Los componentes cliente que sí necesitan inferir el locale en tiempo de ejecución (porque no reciben la prop, p. ej. el botón flotante global) usan usePathname() + localeFromPathname directamente: app/ui/whatsapp-button.tsx:9-11 y app/ui/html-lang-sync.tsx:8-11.

  5. HtmlLangSync (montado una sola vez en app/layout.tsx:62, fuera de los grupos de rutas) corrige en el cliente el atributo lang del <html>, que el layout raíz fija de forma estática en "es" (app/layout.tsx:56):

    useEffect(() => {
  document.documentElement.lang = localeFromPathname(pathname);
}, [pathname]);

    (app/ui/html-lang-sync.tsx:10-12). Esto significa que en el HTML servido estáticamente (antes de hidratación) el atributo lang siempre es "es", incluso para /en/*; se corrige después, en el cliente, tras el primer render.

  6. El selector de idioma de navbar.tsx usa getAlternatePath(pathname, target) (app/i18n/paths.ts:15-19) para calcular a qué URL enlazar al cambiar de idioma, buscando la ruta actual en pathPairs y devolviendo su par.

Flujo 2: pipeline de CI/CD con despliegue condicional

Pipeline único (.github/workflows/pipeline.yml) disparado por pull_request contra master, push a master y workflow_dispatch manual (líneas 20-41).

  1. changes (Plan / Detect Changes), líneas 64-184: hace checkout completo (fetch-depth: 0), calcula el rango BASE..HEAD según el tipo de evento (líneas 86-99) y clasifica cada archivo modificado en web, infra, pipeline, docs u other según su ruta (líneas 109-128). A partir de esas banderas deriva cuatro salidas booleanas consumidas por los jobs siguientes: validate_web, validate_infra, deploy_web, docs_only (líneas 130-154). Un cambio en .github/workflows/ o .github/actions/ (pipeline=true) fuerza la validación de ambas capas, web e infra, aunque el cambio en sí no toque ni app/ ni infra/.

  2. web-quality (Web / Quality Gate), líneas 186-221, condicionado a validate_web == 'true': instala dependencias con la acción compuesta setup-web (npm ci), corre npm run lint, luego npm run build (genera out/), y valida que existan las páginas legales exportadas (out/index.html, out/terminos.html, out/privacidad.html, out/tratamiento-datos.html, out/desuscripcion.html — líneas 206-212). Solo si además deploy_web == 'true' sube out/ como artefacto de build (web-export-<sha>, líneas 214-221).

  3. infra-validate (Infra / Validate CDK), líneas 223-251, condicionado a validate_infra == 'true': instala dependencias de infra/ con setup-infra, corre tsc --noEmit (vía npm run build dentro de infra/) y cdk synth -c stage=prod --quiet, y sube el/los template(s) CloudFormation resultantes como artefacto. Este job valida la infraestructura pero nunca ejecuta cdk deploy — el despliegue de infraestructura es manual (confirmado también por infra/README.md, que documenta cdk deploy -c stage=prod --profile codelabs como comando local).

  4. deploy-web (Deploy / Static Site), líneas 253-306: solo corre si deploy_web == 'true' y el gate web-quality fue exitoso (con infra-validate exitoso u omitido — condición always() con chequeo explícito de resultados, líneas 257-261). Usa el environment: production de GitHub y permisos id-token: write para autenticarse en AWS vía OIDC (aws-actions/configure-aws-credentials, líneas 280-285) sin credenciales estáticas. Sube primero los assets inmutables de _next/static con --cache-control "public,max-age=31536000,immutable" (líneas 287-293), luego el resto del sitio con --cache-control "public,max-age=300,must-revalidate" excluyendo _next/static/ para no pisar la política de cache anterior (líneas 295-300), y finalmente invalida toda la distribución CloudFront (--paths "/", líneas 302-306).

  5. summary (Pipeline / Summary), líneas 308-326: siempre corre (if: always()) y escribe un resumen legible de banderas y resultados en GITHUB_STEP_SUMMARY, independientemente de si hubo despliegue.

Este flujo implica que un cambio puramente documental (docs_only == 'true', es decir, solo toca CLAUDE.md, README.md, context/ o .md) no dispara ni web-quality ni infra-validate ni deploy-web: solo corren changes y summary.
